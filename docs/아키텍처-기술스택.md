## 2. OSS 조사 결과 — 우리 차별점의 "증거"

실제 소스코드/공식문서로 검증(2026-07-04). **레드팀 도구 4개 중 벡터DB 쓰는 곳이 하나도 없음.**

| 도구 | 저장소 | 벡터 검색 | 공격 소스 |
|---|---|---|---|
| **promptfoo** (TS) | SQLite (Drizzle ORM), `src/database/` | ❌ (임베딩은 응답 채점용 `similar`에만) | LLM 생성 + 정적 벤치마크 CSV(exact 카테고리 필터) |
| **garak** (NVIDIA) | JSONL 파일 (DB 없음) | ❌ | 정적 payload 파일 번들 (`garak/data/payloads/`) |
| **PyRIT** (MS) | SQLite / Azure SQL (감사·로깅) | ❌ (임베딩 옵션저장 + brute-force 코사인=분석용) | 정적 YAML 씨앗 + 적응형 LLM 생성 |
| **deepteam** | 영구저장 없음 (JSON 출력) | ❌ | 정적 템플릿에서 LLM 생성 |

**의미 2가지:**
1. **차별점 확정** — 우리 "검색+진화형"(검증된 공격 코퍼스에서 **의미 검색** → 진화)은 이들 중 **아무도 안 함**. 걔넨 (a)LLM 맨땅 생성 or (b)고정 payload exact-match. 우리처럼 대형 코퍼스를 벡터 인덱싱해 RAG 검색하는 곳 없음.
2. **경고(정직)** — 다들 벡터DB를 *일부러* 피함(공격 다양성은 LLM 생성이 더 쌈). 그래서 우리 벡터 검색은 "멋져서"가 아니라 **"검증된 근거(이건 실제로 GPT-4o를 뚫은 프롬프트)"**를 주기 때문에 정당. 이 논리를 못 대면 "promptfoo인데 DB만 붙인 것"이 됨.

**추가 관찰:** 저장하는 도구(promptfoo=SQLite, PyRIT=SQL)는 전부 **관계형** = 우리 Postgres 선택이 업계 표준과 일치. 우리가 더하는 건 그 위에 **벡터 검색 한 스푼(pgvector)**.

출처: `promptfoo/src/database/`, `garak/data/payloads/`, `pyrit/memory/{sqlite_memory,memory_embedding}.py`, `deepteam/attacks/*` (전부 코드 확인, faiss/pgvector=0 hits).

## 3. 컴포넌트별 결정 근거 (기능 → 왜 → 역할)

### 3.1 FastAPI (백엔드)
- **기능**: async 네이티브, Python 생태계.
- **왜**: 공격/LLM 호출이 전부 I/O 바운드 → `asyncio`로 **동시 발사** 유리. 임베딩·데이터셋·판정모델(llm-guard, GPTFuzz RoBERTa)이 전부 파이썬. Spring이면 이 재료를 못 씀.
- **역할**: 대상 등록, 스캔 트리거, 결과 조회, **SSE 진행 스트림**.

### 3.2 PostgreSQL + pgvector (데이터 계층)

**pgvector가 뭔가**: PostgreSQL **확장(extension)**. 별도 제품 아님 — `CREATE EXTENSION vector;` 한 줄로 Postgres에 벡터검색을 켜는 애드온. (엑셀↔엑셀수식 관계). 도커 이미지 `pgvector/pgvector:pg16` = "Postgres + pgvector 미리 설치". **컨테이너 1개 = Postgres+pgvector.**

**내부적으로 뭘 쓰나**:
- 데이터타입 `vector(1536)` = 32비트 float 배열
- 검색 인덱스 **HNSW**(그래프 기반 ANN) 또는 IVFFlat(클러스터) — HNSW는 Pinecone/Weaviate/OpenSearch가 쓰는 것과 **같은 알고리즘**
- 거리 = 코사인 유사도 `<=>`
- ⚠️ pgvector는 임베딩을 **만들지 않음** — 저장·검색만. 텍스트→벡터 변환은 **별도 임베딩 모델**(로컬 sentence-transformers/BGE 무료, 또는 OpenAI API)

**데이터가 어떻게 들어가나 — 2단계:**
- **단계 A 적재(1회, 앱과 무관)**: 공격 60만 → 임베딩 모델 → `INSERT INTO attack_case(prompt_text, attack_type, embedding, verified)` → HNSW 인덱스. = **공격 도서관 구축**.
- **단계 B 사용(앱 등록 시)**: 정찰이 대상 앱 분석 → 프로파일이 **검색어** → pgvector에서 관련 씨앗만 뽑음(60만 → 수십). = 앱 보고 **골라 씀**(직감 맞음).

**테이블 구분(중요)**:
| 테이블 | 내용 | 벡터? |
|---|---|---|
| `attack_case` | 공격 60만 + 임베딩 (도서관) | ✅ pgvector 검색 대상 |
| `Target`/`Scan`/`Attempt`/`Finding` | 앱 정보·스캔결과·진화기록 | ❌ 일반 관계형 |
> 대상 앱 정보는 pgvector에 벡터로 **안 들어감** — "검색어"로만 쓰이고, 자체 데이터는 관계형 테이블에.

**vs OpenSearch (왜 pgvector):**
| | 강점 | 한계 | 우리 결론 |
|---|---|---|---|
| **OpenSearch** | 키워드(BM25)+벡터 **Hybrid Search** | JVM·HNSW 상주메모리 → 리소스↑, 클러스터 필요 | 하이브리드 강점을 우리 검색이 안 씀 → 과설계 |
| **pgvector** | 기존 Postgres 인프라 활용, 관계형+벡터 한 DB | 초대형(수천만+)·고QPS서 성능한계 | **우리 규모(수십만)엔 한계 무관 → 채택** |
- 우리 검색(§5.2 기획) = **메타필터 SQL → 좁힌 수백만 벡터 랭킹**. BM25에 의존 안 함 → OpenSearch의 유일한 강점을 안 씀.
- 우리 차별점(`Attempt.parent_id` 진화트리)은 **JOIN 필요** → OpenSearch는 JOIN 없어 Postgres를 또 띄워야 함(이중저장·싱크).
- 조사에서 벡터DB 쓰는 도구조차 없음 → OpenSearch급 인프라는 명백한 과설계.

### 3.3 Redis — 3역할 (2026-07-10: 5역할→3역할)

**기능적으로 왜 여럿을 하나**: Redis는 "여러 자료구조를 가진 인메모리 서버". 각 역할이 다른 자료구조/키공간을 써서 안 섞임. **브로커는 RabbitMQ로, 실시간(SSE)은 Postgres 폴링으로 분리**했으므로 Redis엔 "빠르고 임시적인 것"만 남는다.

| # | 역할 | Redis 기능 | 우리 프로젝트 |
|---|---|---|---|
| ① | 캐시 | 키값+TTL | **pgvector 씨앗검색 결과 캐시**(같은 프로파일=같은 결과, 벡터검색 비쌈) + 쿼리 임베딩 캐시 |
| ② | rate-limit | `INCR`+`EXPIRE`(TTL) 원자적 카운터 | 여러 워커 429 백오프 좌표 공유(밴회피). 초당 수백 갱신 임시데이터라 인메모리 적합 |
| ③ | result backend | 키값(`SET`/`GET`) | Celery 작업 상태·결과 요약 (공식지원) |

키 네임스페이스로 분리:
```
cache:vecsearch:*     ① 벡터검색 결과 캐시
cache:embedding:*     ① 쿼리 임베딩 캐시
ratelimit:target:xyz  ② 카운터
celery:result:abc123  ③ 결과
```
- 브로커(작업 배달)=**RabbitMQ**, 실시간 진행(SSE)=**Postgres 폴링**으로 각각 분리 → Redis는 rate-limit·캐시·result만.
- 캐시는 3역할 중 근거가 제일 약함(rate-limit·result는 필수) → **히트가 적으면 캐시 역할은 빼도 됨**.

**브로커란**: 메시지를 중개(받아서 전달)하는 미들웨어 = 우체국. FastAPI(보내는이)와 워커(받는이)를 **분리(decoupling)**. "브로커"는 역할 이름, 우리는 그 역할을 **RabbitMQ**가 수행(§3.5).

### 3.4 Celery (워커)
- **기능**: 파이썬 분산 태스크 큐. 브로커(=**RabbitMQ**, §3.5) + result backend(=**Redis**)를 요구.
- **왜**: 스캔이 수 분 + LLM 다중호출 → 요청-응답서 분리 필수. `BackgroundTasks`(PoC)에서 시작 → Celery 승격(독립 스케일·재시작 견딤·재시도).
- **역할**: 스캔 1건 = 태스크 1개. 진화 엔진 전체를 워커가 실행.
- FastAPI↔Celery는 **같은 이미지**, 시작 명령만 다름(`uvicorn` vs `celery worker`).

### 3.5 왜 RabbitMQ (브로커 분리) — 2026-07-10 결정
- Celery 공식문서: *"RabbitMQ(broker) + Redis(backend)"* 조합 = 정석 구성.
- **리뷰 반복 태클**: "Redis는 정식 브로커가 아니다 / 유실 위험" → **브로커만 RabbitMQ로 분리**해 정석 구성 + 태클 원천 차단.
- **역할 층위(중요)**: 작업 큐=**Celery**(정체), 메시지 브로커=**RabbitMQ**(태스크 배달), result backend=**Redis**. "RabbitMQ = 메시지 브로커"가 정확한 표현("샐러리 작업 큐"라 부르면 층위 섞임).
- RabbitMQ는 **브로커만** 함 → Redis는 캐시·rate-limit·result backend(§3.3) 자리로 **여전히 필수**. 둘은 역할이 안 겹침(중복 아님).
- **확장 시**: attempt 이벤트 스트림(스캔당 수천 건, 대량·순서·재생)은 Kafka로 뺄 여지(stretch goal). 작업 큐는 Kafka로 대체 불가(개별 재시도·병렬 안 됨).

**유실 문제 (태클의 진짜 답)**:
- 큐(RabbitMQ)·result(Redis)가 휘발해도 **진실의 원천은 Postgres**(스캔 상태·attempts·findings 원본).
- 결론: **무유실 강배달보장에 매달리지 않음**. 스캔은 재현 가능한 작업 → "잃으면 다시 돌린다".
- ⚠️ **RabbitMQ만으론 부족**: RabbitMQ도 at-least-once라 재전달=중복 가능. 그래서 방어 3종을 함께 둔다:
  1. **Postgres 상태기록** — `pending/running/done/failed` + `updated_at`(하트비트). DB가 진실의 원천.
  2. **태스크 멱등화** — 같은 `scan_id`가 이미 running/done이면 skip(재전달·재시작 중복 방지).
  3. **재시작** — 일시오류=Celery `max_retries`, 워커 급사=하트비트 timeout 감지→스위퍼 재큐잉 or 수동 재시도. MVP는 **failed 감지 + 수동 재시도**면 충분.
- (Celery `task_acks_late`·`task_reject_on_worker_lost`는 이미 설정됨 — 워커 급사 시 재큐잉 보조.)

### 3.6 NGINX (리버스 프록시)
- **리버스 프록시 = 서버 앞 문지기**(안내데스크). 외부는 NGINX만 봄.
- 역할: ①라우팅(`/api/*`→FastAPI) ②TLS 종료(HTTPS) ③로드밸런싱 ④**백엔드 은폐**(FastAPI 포트 외부 미노출) ⑤압축·rate limit.
- ⚠️ 숨기는 건 **백엔드**(서버쪽). 클라이언트 IP는 안 숨김(그건 forward proxy/VPN). 클라 IP는 `X-Forwarded-For`로 백엔드에 전달.
- **vs Traefik**: Traefik=자동설정(Docker 라벨)+자동 HTTPS, NGINX=수동설정+자료 많음. 우리 규모엔 기능차 미미 → **NGINX**(자료·학습가치).

### 3.7 로컬 LLM / 외부 API
- **로컬 LLM(Ollama/vLLM, abliterated)**: "위험한 공격 프롬프트 **생성**"만 격리 담당. 밴 리스크가 attacker 생성에만 있으니 로컬로 빼면 사라짐(§5.3.1). 1차는 Haiku 옵션.
- **외부 API(Anthropic Claude, 주로 Haiku)**: 판정·변이 **극소수 폴백**(L3) + **리포트 AI 요약**(2026-07-07 채택). 밴회피 래퍼 동일 적용. (다이어그램의 'Claude API' 노드)

### 3.8 취약 대상 더미앱
- AcmeBank 챗봇(FLAG123 은닉). 의도적 취약 → **네트워크 격리** 별도 컨테이너. self-testing 전제상 우리가 띄운 대상만.

### 3.9 S3 / MinIO (옵션)
- 증거 트랜스크립트·BrowserActor 스크린샷·리포트 PDF blob. DB엔 메타/포인터, 대용량은 S3. PoC는 로컬디스크 대체.

### 3.10 CI/CD — GitHub Actions (Jenkins 아님)
- **젠킨스도 CI/CD 둘 다 됨**(Pipeline에 deploy stage). CI 전용 아님. 근데 **자체 호스팅 서버(EC2 하나 더)** 필요.
- GitHub Actions = 호스팅형, GitHub 네이티브, **서버 추가 0** → 우리 규모에 적합.
- 흐름: `push → Actions(빌드·테스트·이미지=CI) → EC2 SSH 배포(CD)`.

### 3.11 관측성 스택 (Prometheus · Grafana · Loki · Jaeger → Slack)
- **왜**: 스캔이 수 분·다단계(정찰→검색→발사→판정→변이)라 **관측 없이는 어디서 느리고 실패하는지 진단 불가**. "진화가 실제로 도는가"도 메트릭으로 확인.
- **Prometheus**(메트릭 수집): FastAPI/Celery가 `/metrics` 노출 → 스캔 수·세대당 시간·판정 지연·LLM 호출 수·워커 큐 길이·에러율 수집.
- **Grafana**(시각화·경보): Prometheus 데이터 대시보드 + **alert** → Slack 발송.
- **Loki**(로그 집계): 구조화 로그를 한 곳에서 검색. ELK보다 가벼움(Grafana 생태계 통합).
- **Jaeger**(분산 트레이싱): "요청 → FastAPI → Celery 워커 → 액터 → LLM"의 한 요청 전체 경로·구간 지연 추적 → 진화 파이프라인 병목 진단.
- **Slack**: Grafana 경보(에러율↑·워커 다운)·스캔 완료/실패 알림을 팀 채널로.
- **배포**: EC2의 **Docker 컨테이너 하나**로 묶어 구동(다이어그램 좌하단 모니터링 박스).
- **PoC 범위**: 관측성은 **운영/확장 단계** 항목 — PoC 데모엔 없어도 되고, 아키텍처 완성도·운영 고려를 보여주는 용도.

## 4. 전체 스캔 흐름 — 언제 뭐가 도나

```
0. 적재(1회):      공격60만 → [임베딩모델] → [pgvector] 도서관 구축
1. 등록:           브라우저 →[NGINX]→[FastAPI]→ Target저장[Postgres]
2. 스캔시작:       [FastAPI] 태스크 큐투입[RabbitMQ] + Scan생성[Postgres], task_id 즉시반환
3. 워커실행:       [Celery] 브로커서 꺼냄[RabbitMQ] → 진화엔진:
   3-1 정찰:       리포 grep+AST(0토큰) → 프로파일
   3-2 씨앗검색:   프로파일→[pgvector] 메타필터+벡터 → 수십개 (결과캐시[Redis①])
   3-3 발사:       [HttpActor]→[취약앱] (429백오프 좌표[Redis②])
   3-4 판정:       룰+카나리(FLAG)+llm-guard (애매시 [Haiku]폴백)
   3-5 변이:       [로컬LLM]생성 or [pgvector]검색, Attempt·ScanEvent저장[Postgres]
   3-6 실시간:     워커→scan_events 기록[Postgres] → [FastAPI SSE]가 DB 폴링(id>after) → 프론트 관전
4. 종료:           Finding저장[Postgres], 결과요약[Redis③], 증거[S3]
5. 대시보드:       프론트→[FastAPI]→[Postgres] 히트맵·진화트리 조회
개발:              GitHub→Actions→EC2 배포
```

## 5. 비교표 모음 (발표용)

**OpenSearch vs pgvector** → §3.2
**RabbitMQ(브로커) + Redis(캐시·rate-limit·result)**: 브로커는 정식 RabbitMQ로 분리(유실 완화·태클 차단), Redis는 인메모리 강점 자리(rate-limit 카운터·벡터검색 캐시·결과저장). 역할 안 겹침.
**NGINX vs Traefik**: 기능차 미미, NGINX=자료·학습가치 → NGINX
**GitHub Actions vs Jenkins**: Actions=서버0 호스팅형, Jenkins=자체서버 필요 → Actions

## 6. 발표 방어 논리 (예상 질문 → 답)

- **"왜 pgvector, OpenSearch 아니고?"** → 우리 검색이 메타필터→벡터라 OpenSearch 하이브리드 강점을 안 씀. 관계형(진화트리) JOIN 필요. 수십만 규모라 pgvector 한계 무관. 레드팀 도구 4개 중 벡터DB 쓰는 곳조차 없음.
- **"브로커가 Redis면 유실/정식 아님 아니냐?"** → 맞아서 **브로커를 RabbitMQ로 분리**(정석). Redis는 캐시·rate-limit·result backend. 유실은 브로커만으론 안 되니 **Postgres 상태기록+멱등+재시작**을 함께 둔다. 스캔은 재현 가능이라 "잃으면 다시".
- **"promptfoo 이미 있는데 차별점?"** → 그들은 LLM 생성/고정 payload. 우리는 **검증된 공격 코퍼스 벡터검색+진화**(RAG). 4개 도구 중 유일. 근거 있는 공격.
- **"실시간(SSE)은 어떻게? Redis Pub/Sub?"** → Pub/Sub은 컨슈머 내려가면 유실 → **Postgres 폴링 SSE**로 변경. 워커가 scan_events를 DB에 쓰고 프론트가 "마지막 id 이후"(`?after=`) 재조회. offset=DB PK라 유실·복구 문제 없음.
- **"Kafka 왜 안 씀?"** → Kafka는 작업 큐 대체 불가(개별 재시도·병렬 안 됨, head-of-line 블로킹). 작업 큐는 Celery. Kafka는 attempt 이벤트 스트림 자리에 stretch goal로만.
