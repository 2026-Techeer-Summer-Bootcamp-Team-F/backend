# 공격 시나리오 설계 — 대상 상태·컨텍스트별

> **목적**: 대상 앱을 "한 가지 상황"이 아니라 **여러 상황**(로그인/비로그인, 역할, 앱 종류, 방어, 부작용)에서 공격해야 진짜 취약점을 찾는다. 어떤 시나리오들이 있고, 무엇을 먼저 지원할지 정리.
> **계기**: 멘토 피드백(2026-07-08) — *"로그인했을 때 하냐 / 안 했을 때 하냐 같은 여러 시나리오를 더 생각해보라."* 방향은 맞게 가고 있으니 시나리오를 넓혀 설계에 반영.
> **전제**: 우리 도구 = **인가된 대상**(내 앱 또는 **점검 위임받은 고객사 앱**)을 자동 레드팀. self-testing은 PoC 범위, 실제 서비스는 **타인(고객) 앱 점검**이 목표 → 그래서 인증·부작용 시나리오가 더 중요해진다.
> **데모 방식 (확정, 2026-07-08)**: PoC/시연은 **자체 더미앱을 "고객사 앱처럼" 띄워** 점검한다. 즉 로그인·역할(게스트/유저/관리자)·도구를 갖춘 **가짜 고객사 앱**을 직접 세우고 그 위에서 아래 시나리오를 실증 → 인가·법적 장벽 없이 §1~§6를 그대로 시연, 실제 고객사 앱 확장 시 방식 동일.
> 관련: `기획.md §5`, `액터-인증-설계.md`(토큰 발급/갱신), `정찰-액터자동구성-설계.md`, `ERD-완전정리.md`(scans.config), `NEXT.md`.

---

## 0. 왜 시나리오를 나눠야 하나

대상을 **한 상태로만** 찌르면 진짜 취약점을 놓친다. 특히 **인증 상태에 따라 공격 표면이 통째로 달라진다**: 비로그인에선 못 닿는 데이터·도구가 로그인하면 열린다. 그래서 "이 앱이 뚫리나?"가 아니라 **"어떤 상태에서, 누구로, 뭐가 뚫리나?"**를 물어야 한다.

---

## 1. 접속·인증 상태 (★핵심 축 — 멘토 포인트)

| # | 시나리오 | 설명 | 새로 열리는 공격 표면 |
|---|---|---|---|
| A1 | **비로그인 (공개 챗봇)** | 로그인 없이 바로 공격 | 시스템 프롬프트 유출, 탈옥, 일반 정보 유출 |
| A2 | **로그인 필요 → 인증 후 공격** | 토큰 받아서 공격 (→ `액터-인증-설계.md`) | A1 + 로그인 전제 기능 전체 |
| A3 | **비로그인 상태 vs 로그인 상태 각각** | 같은 앱을 두 상태로 나눠 스캔 → 비교 | 상태별 차이가 곧 리포트의 핵심 인사이트 |
| A4 | **역할(권한)별: 게스트 / 일반유저 / 관리자** | 계정 등급을 바꿔가며 공격 | 권한 상승, 타인 데이터 접근(IDOR류), 관리자 기능 오용 |
| A5 | **세션 상태** | 세션별 격리·쿠키/세션 유지 필요 여부 | 세션 고정·세션 간 데이터 누수 |

**핵심 통찰 (이게 멘토 포인트의 실체):**
로그인 여부는 단순 "접속 방법"이 아니라 **공격 표면 자체가 달라지는 것**이다.
- **비로그인**: "시스템 프롬프트 뱉어봐", "탈옥" 정도만 가능.
- **로그인 상태**: **내 계정 데이터·타인 데이터 조회, 도구 실행(이메일/이체), PII 유출** 등 훨씬 위험한 표면이 열림.
- → 이상적 리포트 = **두 상태를 다 스캔해 "어느 상태에서 뭐가 뚫리나" 비교.**
  예: *"비로그인은 안전. 그러나 일반유저로 로그인하면 프롬프트 인젝션으로 **타인 PII 유출**됨(critical)."*

## 2. 대화 상태 (턴 수)

| 시나리오 | 설명 | 엔진 영향 |
|---|---|---|
| **단일턴** | 매 요청이 새 대화(맥락 없음) | 현재 기본. 씨앗/변이 한 방 발사. |
| **멀티턴** | 앱이 대화 맥락을 기억 | **크레센도**(조금씩 유도해 뚫기)가 가능해짐. 엔진이 세션을 유지하고 대화 히스토리를 이어붙여야 함. |

→ 대상이 대화를 기억하는지는 **정찰/프로빙**으로 파악. 멀티턴 크레센도는 **후순위**(단일턴 먼저).

---

## 3. 앱 종류·능력

| 종류 | 추가로 생기는 공격 | 판정 포인트 |
|---|---|---|
| **순수 챗봇** | 기본(인젝션·탈옥·유출) | 응답 텍스트 |
| **RAG**(문서 검색) | 문서에 악성 지시 심기 = **간접 인젝션**(T0051.001) | 검색된 문서 지시를 따랐나 |
| **에이전트**(도구: 메일·DB·결제) | **도구 오용·과잉 권한**(T0053) | 도구가 실제로 잘못 호출됐나 |
| **멀티모달**(이미지 입력) | 이미지 속 인젝션 | (후순위) |

→ 앱 종류는 정찰의 `tools`/`rag_sources` 값으로 파악(→ `ERD-완전정리.md` target_projects).

---

## 4. 방어 수준

무방어 / 입력필터·모더레이션 / 출력필터(비밀 마스킹) / 시스템프롬프트 강화 / WAF·rate limit.
→ **방어가 뭐가 있냐에 따라 먹히는 전략이 달라짐.** 정찰(`defences`)로 미리 파악 → 우회형 씨앗(인코딩·다국어 등) 우선 선택. (기획 §5.1 정찰 → 씨앗 필터)

---

## 5. "뚫림" 판정 시나리오 (앱마다 성공 기준이 다름)

| 대상 | 판정 방법 | 상태 |
|---|---|---|
| **카나리 심은 우리 더미앱** | FLAG 문자열 매칭(오탐 0%) | ✅ 동작 |
| **실제 고객사 앱(카나리 없음)** | PII 패턴 매칭 / 정책 위반 감지 / (애매하면) 작은 LLM 판정 | ⏳ 필요 |
| 목표별 성공 기준 | 시스템프롬프트 유출 / PII 유출 / 유해 콘텐츠 / 도구 오용 — 각각 다름 | ⏳ 유형별 정의 |

→ **실제(남의) 앱을 겨냥하려면 카나리 없는 판정이 필수.** (기획 §5.5 3계층 판정 확장)

---

## 6. 안전·부작용 (⚠️ 실제 앱 점검 시 중요)

| 시나리오 | 위험 | 대응 |
|---|---|---|
| **행동형 에이전트** (진짜 메일 전송·이체) | 공격이 **실제 부작용**을 일으킴 | **안전모드/드라이런**(도구 호출을 실제로 안 하고 시뮬레이션), **샌드박스** 대상 |
| **프로덕션 대상** | 실데이터 오염·실제 고객 알림 발송 | **스테이징 환경 권장**, prod는 rate·범위 제한 |

→ "찌르기만 하면 되는" 텍스트 챗봇과 달리, **에이전트는 공격이 곧 실행**이 될 수 있음 → 안전장치 없이는 위험.

---

## 7. 인가·교전 규칙 (Rules of Engagement)

내 앱 vs **고객사 앱**(위임) — 허용 엔드포인트 범위, 점검 시간대, rate 합의, 대상 소유/권한 확인.
→ PoC/데모는 **자체 더미앱을 고객사 앱처럼(로그인·역할·도구 포함) 구성해 점검** → 인가 장벽 없이 §1~§6 시나리오를 실제 시연. 실서비스 확장 시 등록 단계에서 **점검 권한 확인 절차** 추가(기획 §11.1, 결정로그 E1에서 verify 컬럼은 뺐지만 "권한 확인" 개념은 유지).

---

## 8. 우선순위 — 지금 락(lock) vs 나중

**지금 시나리오로 못박으면 좋은 것 (설계 영향 큼):**
1. **인증 컨텍스트별 스캔** — 스캔에 "비로그인 / 유저 / 관리자" 컨텍스트를 넣고 상태별로 나눠 스캔 → 리포트 비교. (A3·A4 = 멘토 포인트의 구현형)
2. **카나리 없는 판정** — 실제 앱 겨냥의 전제(§5).
3. **안전모드(드라이런)** — 행동형 에이전트 대비(§6).

**후순위(나중):** 멀티턴 크레센도(§2) · RAG 간접 인젝션/에이전트 도구오용의 정밀 판정(§3) · 멀티모달 · 브라우저 액터(별건, 후순위 확정).
